# audit_wiki 模块详细规则

## 模块目标
定期或按需扫描 `wiki/` 目录，检测健康度问题并提供修复建议。本模块只负责诊断，写入修复由 `persist_knowledge` 或人工执行。

---

## 检查清单

| 检查项 | 方法 | 报告格式 |
|--------|------|----------|
| 矛盾点 | 对比同一主题在不同页面中的同级描述 | `⚠️ 矛盾: 页面A说 X，页面B说 Y` |
| 过时信息 | 检查元数据 `updated` 字段（180天阈值） | `⏰ 过时: 页面X最后更新于 180 天前` |
| 孤儿页 | 检查反向链接区块是否空或缺失 | `🔗 孤儿页: wiki/xxx.md 无反向链接` |
| 缺失关联 | 主题相似但页面间无交叉引用 | `🔗 建议链接: A.md ↔ B.md` |
| 置信度退化 | 统计低置信度页面占比 | `📉 低置信度页面占 N%` |
| 归档候选 | 过时且无反向链接的页面 | `📦 归档建议: wiki/xxx.md` |
| 人工复核标记缺失 | 低置信度页面是否缺少 `[⚠️ 待复核]` 标签 | `🏷️ 缺失标记: 页面X为低置信度但无待复核标签` |
| **YAML 语法错误** | 检查 `---` 包裹是否完整，必填字段 `created`/`confidence` 是否存在，值格式是否正确 | `📛 格式损坏: 页面X 的 YAML frontmatter 无效 (原因: ...)` |

---

## 维护报告格式

扫描完成后输出结构化的健康检查报告：

## Wiki 健康检查报告
检查时间: YYYY-MM-DD HH:MM

### 发现的问题
1. [问题类别] 问题描述
2. ...

### 建议行动
1. [操作建议]
2. ...

### 推荐阅读
- [主题] — 建议查阅来源

---

## 归档执行流程

当检查清单生成 `📦 归档建议` 后，在报告的“建议行动”中，应列出具体的归档操作步骤，并询问用户是否立即执行。流程如下：

1. **生成归档草案**：列出所有建议归档的页面，对每个页面给出以下信息：
   - 页面路径（如 `wiki/entities/outdated-tool.md`）
   - 最后更新日期
   - 是否有反向链接
   - 建议移动到 `wiki/archive/` 的理由

2. **展示给用户确认**：

   ## 📦 归档建议详情
   | 页面 | 最后更新 | 反向链接 | 归档理由 |
   |------|----------|----------|----------|
   | wiki/entities/outdated-tool.md | 2025-01-15 | 无 | 过时 >180天，无引用 |
   
   是否将以上页面归档？归档操作包括：
   - 移动页面到 `wiki/archive/` 目录
   - 从 `wiki/index.md` 移除对应条目
   - 清除其他页面中指向该页面的反向链接
   - 追加操作记录到 `wiki/log.md`
   
   请回复 **Y** 执行归档，或 **N** 跳过。


3. **用户确认后执行归档操作**：
   - 将页面文件从原位置 **移动** 到 `wiki/archive/`（保留文件名不变，若冲突追加归档日期）
   - 在 `wiki/index.md` 中找到并删除对应的索引条目
   - 扫描所有 Wiki 页面，删除指向该页面的 `[[wiki/xxx]]` 链接及对应反向链接区块条目
   - 在 `wiki/log.md` 追加记录：
     ```
     YYYY-MM-DD HH:MM [audit_wiki] 归档 wiki/entities/outdated-tool.md → wiki/archive/
     ```
   - 告知用户归档完成

4. **归档后不自动触发其他模块**，流程结束。

> 注意：归档操作由审计模块直接执行，无需调用 `persist_knowledge`。

## 知识沉淀触发
审计过程中，若通过矛盾检测或缺失关联分析发现了可形成新结论的洞察（例如两个矛盾页面可被统一解释，或发现了一个应该存在但缺失的概念），**必须立即加载并遵循 `references/persist_knowledge.md`**，生成新页面草案并等待用户确认。流程同查询触发回写。

---

## 操作日志追加
每次审计完成后，**必须** 在 `wiki/log.md` 末尾追加一条记录：

```
YYYY-MM-DD HH:MM [audit_wiki] 审计完成，发现 X 个问题，Y 条建议
```

示例：
```
2026-05-01 09:00 [audit_wiki] 审计完成，发现 2 个矛盾，3 个孤儿页，建议归档 1 条
```

## 指标度量
每次审计应计算并报告以下指标：

| 指标 | 定义 | 目标 |
|------|------|------|
| 摄入吞吐量 | （不在审计中计算） | - |
| 查询精确度 | （不在审计中计算） | - |
| 知识新鲜度 | 180 天内更新的页面占比 | ≥70% |
| 孤儿页率 | 无反向链接页面占比 | <10% |
| 覆盖度 | 已索引知识点 / 总检测知识点 | ≥95% |
| 低置信度占比 | 低置信度页面 / 总页面数 | 建议 <20% |
| 目录同步率 | wiki/ 子目录下存在的 .md 文件中，其相对路径未在 wiki/index.md 的链接中出现的文件占比 | <5% |

---

## 下次审计建议
报告末尾自动计算并输出下一次建议审计的时间：
- 若本次发现问题较多（≥5 个），建议 15 天后再次审计
- 若问题较少（<5 个），建议按常规 30 天间隔
- 将此日期写入报告末尾，并提示用户可将其填入 `wiki/index.md` 的 `下次建议审计` 字段。

> 下次建议审计日期: YYYY-MM-DD

---

## 模块结束规则
- 审计报告呈交用户后，**不得自动触发** `query_knowledge`、`persist_knowledge` 或再次调用自身，除非用户明确要求。
- 若用户针对报告中的问题提出询问，按用户新指令处理。
